# Performance is part of product correctness

Read during implementation and stage 5 of [docs/discipline.md](docs/discipline.md). The target is an immediate-feeling, smooth long page on iPhone 17 Pro and Pro Max. A visually correct section that introduces unnecessary wait, blocking work, layout shifts, or interaction lag has not passed. Preserve approved visual quality while minimizing runtime cost. The 95+ mobile Lighthouse goal is a measured target, never an assumed result.

## The 32,127-pixel background

`background.png` and `background_text.png` are each about 44 MB. The latter is a reference only. Do not serve either entire PNG as a single production background. Start with the clean artwork, split it at natural section boundaries or into tiles, and test compressed modern formats and responsive widths. Preserve crop, color, sharpness, and overlay alignment at target device pixel ratios. Compare boundaries pixel by pixel and while scrolling; there must be no seams, blank bands, late pop-in, or visible quality drop.

Make the first visible artwork ready immediately; load later sections before they enter view. Reserve their layout space so the long page cannot jump. Measure payload, decode cost, memory pressure, and scrolling behavior. Choose the simplest segmented delivery that meets the visual and speed gates; splitting alone does not guarantee improvement.

## Rendering and asset priority

1. Prioritize the first viewport: background/hero, primary typography, CTA, and first controls. Do not lazy-load the LCP image. Preload only assets proven critical; excessive preloading competes with the hero.
2. Prefer prerendered HTML for stable public content, Server Components for server-only work, and small Client Components for actual interaction. Use request-time SSR when content truly depends on the request or cannot meet its freshness needs through prerendering/revalidation, and that benefit outweighs added server latency. Use client-only rendering only when browser state makes server HTML unhelpful. Stream slow request-time sections with Suspense only when it improves the visible result; do not make static content wait behind a dynamic boundary.
3. Use correctly dimensioned responsive images (`next/image` where appropriate), efficient modern formats and quality, and phone-sized resources for phones. For this page's long continuous artwork, request later compressed tiles eagerly at low priority and show their tiny inline previews until decode; the first tile retains high priority. This prevents empty bands during a fast scroll or cold reload. Lazy-load unrelated later images, video, optional components, and third-party scripts. Provide still-image fallbacks for deferred video.
4. Use `next/font` or optimized self-hosted fonts. Ship only the used families, weights, and subsets; reserve metrics to avoid text reflow. Prevent image, font, and animation layout shifts.
5. Keep the client bundle and hydration small. Prefer CSS/native browser behavior; avoid render-blocking dependencies, oversized state, expensive effects, and unnecessary React renders. Dynamic imports, `React.lazy`, transitions, deferred values, and View Transitions are conditional tools, not a feature checklist; use one only when supported and measured to help.
6. Animate transform and opacity rather than layout properties. Keep scroll and input responsive while background work occurs. Use caching, CDN/static delivery, production minification/compression, and framework caching where appropriate; verify freshness and cache isolation for dynamic or user-specific data.

## Measure, then choose the rendering strategy

At implementation, record why each route or significant section uses static prerendering/SSG, request-time SSR, or client-side rendering/CSR, and where its Server/Client Component boundary sits. These are different decisions: Server Components may be prerendered or rendered on request, while Client Components can appear in initial server HTML and then hydrate. Start with the smallest client graph that satisfies real behavior.

In a production build, compare relevant alternatives when a measured bottleneck or data requirement warrants it. Use comparable device, network, and cache conditions. Check cold navigation and repeat navigation, TTFB, FCP/LCP, INP where measurable, CLS, transferred JavaScript and image bytes, hydration/long tasks, server response and cache behavior. If request-time SSR adds delay without needed freshness or personalization, prerender or cache that content. If client rendering delays useful content or interaction, move appropriate work to the server and reduce shipped JavaScript. If server rendering or streaming demonstrably improves the user path, use it for that path. Verify behavior, data correctness, SEO-visible content, and reference fidelity again after any change. Do not add a technique merely because it exists or assume it is faster without measurement.

## Production measurement gate

Run `next build` and a production server (`next start` where applicable), not only a dev server, at the primary mobile viewport. Inspect the build's route-rendering output, browser network, console, and performance traces. Record transferred asset and JavaScript bytes, critical request order, TTFB, FCP/LCP, CLS, image/font flashes, scroll/animation smoothness, and interaction latency. Measure INP only from a representative interaction session or field data; do not report a synthetic page-load number as INP. Test cold initial navigation and a representative long scroll. Fix meaningful regressions, then measure again and repeat affected visual comparisons. Report real measurements and conditions; never claim a score or “instant” experience without evidence.
