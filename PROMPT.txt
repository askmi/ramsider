### Frontend Performance Requirements

Performance is a primary product requirement. The site must feel instant on modern mobile devices, especially iPhone Pro.

Core rule

Do not consider a feature complete if it is visually correct but introduces unnecessary loading, rendering, JavaScript, layout shifts, blocking work, or interaction latency.

Required practices
Prefer Next.js Server Components. Use Client Components only when interactivity requires them.
Prefer SSR/static rendering for above-the-fold content. Stream slower content with Suspense when appropriate.
Use React.lazy, dynamic imports and code splitting for non-critical components.
Use startTransition, useTransition and useDeferredValue for non-urgent updates when they improve responsiveness.
Use modern React features only when they measurably improve UX; do not add complexity without benefit.
Minimize shipped JavaScript and hydration.
Lazy-load below-the-fold images, components and third-party scripts.
Never lazy-load the primary LCP/hero asset. Preload/prioritize critical visual assets.
Use next/image where appropriate with correct dimensions, responsive sizes, modern formats and optimized quality.
Use next/font or optimized self-hosted fonts. Load only required families, weights and subsets.
Avoid font-induced layout shifts.
Use responsive image/background assets; never ship unnecessarily large desktop assets to mobile.
Optimize background images for correct crop, resolution and device pixel ratio.
Preload only genuinely critical resources; avoid excessive preload.
Avoid render-blocking third-party scripts and dependencies.
Keep dependencies minimal and tree-shakeable.
Prefer CSS/native browser capabilities over JavaScript when practical.
Keep animations on compositor-friendly properties such as transform and opacity; avoid layout-heavy animations.
Prevent unnecessary React renders, expensive effects and large client state.
Use caching, CDN/static delivery and Next.js caching where appropriate.
Enable production minification/compression and optimized production builds.
UX constraints

The initial viewport must appear immediately useful.

Prioritize:

hero/background;
primary typography;
primary CTA;
first interactive elements.

Below-the-fold content must not delay initial rendering.

Interactions must remain responsive while background work occurs.

Performance validation

Before marking the task complete:

test the production build, not only dev mode;
test the primary mobile viewport;
inspect network requests and transferred JS/assets;
inspect browser console and performance traces;
verify no unnecessary blocking requests;
verify no visible layout shift or font/image flash;
verify scrolling and animations remain smooth;
check Core Web Vitals, especially LCP, INP and CLS;
fix meaningful regressions before completion.

After every substantial UI change, re-check visual fidelity and performance.

Priority

When trade-offs exist:

visual fidelity + immediate UX + low interaction latency > implementation convenience.

Do not sacrifice the approved design, but achieve it with the smallest practical runtime cost.

React 19.3 возможностям вроде Suspense, transitions и View Transitions, а также текущим Next.js рекомендациям по оптимизации fonts/images

# Visual Verification

Never consider a UI task complete based only on source-code inspection.

For every visual UI task:

1. Start the application.
2. Open the target page in a real browser.
3. Set the browser viewport to the required reference size.
4. Wait until:
   - fonts are loaded
   - images are loaded
   - animations affecting layout have stabilized
5. Capture a screenshot.
6. Compare the screenshot against the corresponding reference image.
7. Inspect differences in:
   - element position
   - width and height
   - spacing
   - alignment
   - typography
   - font size
   - font weight
   - line height
   - colors
   - borders
   - border radius
   - shadows
   - image crop
   - background positioning
   - responsive behavior
8. If meaningful differences exist:
   - identify the cause
   - modify the implementation
   - reload the page
   - capture another screenshot
   - compare again
9. Repeat until the implementation satisfies the acceptance criteria.

Never report completion without performing the final browser verification.

A successful build, passing TypeScript, or passing unit tests does NOT mean
the UI implementation is complete.

The final response must report:

- viewports tested
- screenshots compared
- visual differences remaining
- interaction tests performed
- browser console errors

Это намного важнее какого-нибудь универсального frontend-development skill.

Skills как раз предназначены для кодирования такого повторяемого workflow — instructions + supporting resources/scripts.

7. Но НЕ делай требование pixel diff = 0%

Это будет ошибкой.

Причины:

font antialiasing;
subpixel rendering;
browser differences;
OS differences;
shadows;
image interpolation;
transforms;
fractional coordinates.

Даже Playwright предупреждает, что screenshot rendering может различаться из-за OS, browser version, hardware и окружения.

Поэтому лучше что-нибудь вроде:

Pixel difference: < configurable threshold

AND

Visual agent:
    no material layout/design differences

А не:

difference === 0

12. Я бы добавил ещё один Skill: implement-render

Он должен заставлять Codex сначала декомпозировать изображение, а не сразу кодить.

Например:

# Render implementation workflow

Before coding:

1. Inspect the reference render.

2. Identify:
   - page sections
   - content boundaries
   - reusable components
   - backgrounds
   - foreground assets
   - text layers
   - interactive elements
   - likely responsive behavior

3. Determine which visual content should remain an image and which
   should be implemented as HTML.

4. Do not reproduce interactive text/buttons as baked-in pixels.

5. Preserve the provided artwork whenever possible.

6. Implement overlays using semantic HTML.

7. Match the reference at its native viewport before implementing
   responsive variants.

8. After implementation invoke the visual verification workflow.

Это особенно важно для твоего кейса.
