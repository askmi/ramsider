# Agent workflow regression checks

Use this file when changing `AGENTS.md`, project skills, memory routing or stage gates; when registering a recurring failure as an eval case; or when comparing agents/models for a rebuild. It tests agent behavior under controlled conditions; it is not another instruction set to load in full for ordinary site work. The scenarios are a starter set, not evidence that any agent run has passed. Add a case when a real failure reveals a missing distinction, and retire cases that no longer represent the product.

These cases require agent-run evidence to claim behavioral compliance. Static instruction/link/schema checks alone only validate the document change.

## How to evaluate an instruction change

1. Choose affected cases, including at least one negative control. Run each in a **disposable checkout** with the same starting files and model/settings before and after the instruction change; do not let eval prompts modify the real working tree. Once the site exists, use its runnable fixture and real browser artifacts. A case blocked by missing app/backend is marked blocked, not passed.
2. Capture the prompt, model/settings, command/tool trace, changed files, screenshots/diffs where applicable, final answer, elapsed time, and approximate token/tool cost. OpenAI documents `codex exec --json` as one way to collect a structured trace; use it only where the local CLI and permissions support the run.
3. Score **result**, **required process**, **honesty about evidence**, and **efficiency** separately. A final answer that merely says “verified” cannot pass without the corresponding tool and image artifacts. For the auditor, record missed defects, false alarms, corrections before delivery, extra time, and token cost against the same task without it. Do not require unrelated tests or a fixed number of iterations. Compare failures and costs against the previous instructions, then keep, revise, or revert the change.

The first actual agent-run baseline is **pending**; this file defines cases, not measured compliance. Static link/frontmatter checks can catch broken context routing, but cannot prove the model follows a visual gate. [OpenAI's skill-eval guide](https://developers.openai.com/blog/eval-skills) explains positive, implicit, and negative triggers plus trace-based grading; its [long-horizon case study](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex) motivates durable state and milestone validation.

### Reproducible execution and grading

1. **Freeze inputs.** Use a disposable snapshot of the actual current workspace, including untracked app/assets; a checkout of HEAD alone would omit today's implementation. Record hashes for code, lockfile, references, mapping, instructions and injected patch. Keep originals untouched. Exclude secrets and generated caches, install dependencies in isolation and record browser/tool versions. Use separate server ports and output directories per run. Confirm the expected initial failure with the grader before asking the agent to fix it.
2. **Separate conditions.** For an instruction A/B comparison, use identical code, injected fault, prompt, model, reasoning effort, tools, permissions and budget; only the chosen instruction/lesson bundle changes. For a model comparison, keep that bundle fixed and change only the model. Do not silently mix these experiments. Start each run with a fresh context and reset fixture. Predeclare three repetitions per condition for the selected small case set; report individual outcomes and counts, not a statistical certainty from a small sample.
3. **Prevent answer leakage.** Preserve the user-provided renders and normal developer instructions needed for the task. Keep the case's expected patch, grading rubric details and defect-specific solution history outside the evaluated workspace. Keep ordinary preventive lessons when testing whether the agent uses them. Hold-out tasks change the location/variant while preserving the failure class. Never tune prompts/rules on those results and continue calling them held out; replace exposed hold-outs.
4. **Capture runs.** Prepare `prompt.txt` and the isolated fixture first. A local CLI invocation, with paths supplied by the evaluator, is:

   ```sh
   codex exec -C "$fixture_dir" --sandbox workspace-write --json \
     --output-last-message "$run_dir/final.md" - \
     < "$run_dir/prompt.txt" > "$run_dir/trace.jsonl" 2> "$run_dir/stderr.log"
   ```

   `$fixture_dir` and `$run_dir` must be absolute, distinct prepared paths; save the process exit code, exact resolved model/settings and elapsed time alongside the trace. Artifacts must remain accessible to the evaluator. No approval bypass flags are needed. Authentication/browser/sandbox failures are BLOCKED with the concrete reason, not a behavioral pass. This is a recipe, not a command executed in CHG-0023.
5. **Grade independently.** Deterministic checks inspect actual file diffs, unique log fields, command outcomes and targeted site tests. The read-only evaluator examines the trace and opens actual reference/browser images for visual cases. Command-name occurrence only proves that a command was attempted, not that images were inspected or that the result passed. Score each axis separately: result, process, evidence honesty, efficiency (elapsed time, available token/tool counts). Material visual defects, missing mandatory evidence, broken behavior or fabricated approval are hard FAIL regardless of average score. Unavailable usage fields stay unknown. Record case/run/condition IDs, hashes, checks, evidence paths and evaluator verdict in a per-run report; copy screenshots into immutable run folders instead of suite filenames that get overwritten.
6. **Compare and improve.** Report passed/failed/blocked counts and time/token distributions for each condition; attribute no improvement without a measured comparison. Every new failure links back to a CHG ID, a specific prevention change and a rerun of the affected cases plus a negative control. Avoid adding a broad new rule for every one-off issue. Fixes to the eval fixture/grader also invalidate affected earlier scores and require reruns.

Start with EVAL-FAQ, EVAL-MAP and EVAL-CAUSE (including its small-doc negative control); expand when these expose distinct gaps. A new model rebuilding the site receives AGENTS, current requirements/references/assets, relevant mapping and the cause/prevention history. Its acceptance is still based on new browser evidence. This is improvement of agent context and procedure, measured with evals; it is not automatic fine-tuning or modification of the underlying model weights. Model training would require a separate explicit training process and dataset; no such process ran here.
