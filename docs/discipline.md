# Development discipline: one request, complete result

The user's “one iteration” means one request to Codex should trigger a complete internal development cycle. It does **not** mean one code edit or one screenshot. Codex owns the repeated diagnosis and repair until all applicable gates pass. Do not transfer routine QA back to the user. A pass is evidence-based: there may be unknown bugs, but no known material mismatch, broken interaction, failing check, or unexamined requirement can be called done.

Work on a visual slice small enough to compare with the reference, then integrate **every slice in the requested scope** into the full scroll page. A passed slice is an internal milestone, not a handoff. At the start of each slice, make a compact coverage record from the render: content/art, controls and destinations, viewport/locale states, and relevant speed risks. Give each applicable check a result of pass, fail, or blocked with evidence; do not equate “not yet tested” with pass. For every stage, keep the target, observation, defect, fix, and recheck clear. A failed gate routes work back to the responsible stage and reopens downstream checks affected by the change.

Decide routine implementation details from the render, assets, code, and product brief without pausing for intermediate user approval. Reproduce visible reference copy in the local build for fidelity, with unverified factual claims tracked for publication. When a required media file, destination, credential, confirmed price/claim, or commerce behavior is genuinely absent, finish independent sections and checks, isolate the missing dependency, and ask only for the external input needed to finish that behavior or publish it. Do not invent it, silently omit a visible control, or mark that control complete. Keep a blocked gate distinct from a failed implementation that Codex can fix itself.

Do not treat the stages as a waterfall. After any visual fix, rerun the affected screenshot comparison. After refactoring, revisit affected interactions and visuals. After an image/font/loading optimization, revisit both performance **and** visual fidelity. A section is not finished until its local loop passes; the page is not finished until integration checks pass across the long scroll. Include a final assembled-page screenshot/scroll pass after all local slice passes, so small per-section alignment errors cannot accumulate unnoticed.

For substantive project work, send the [non-editing discipline auditor](supervision.md) the relevant artifacts at each applicable gate, including the final evidence summary. Its independent finding is another checkpoint, not a substitute for executing the gate. If it finds an unrun feasible check, run it before moving on; if it finds a defect, repair and re-audit the affected gate. The auditor also reviews outputs from any other agents at the relevant checkpoint. Keep its handoff concise so independent review does not duplicate the full implementation context.

Keep the test matrix proportionate without skipping requirements: compare each affected English slice to the render on Pro, inspect Pro Max and representative other widths, automatically check translation-key coverage and overflow for **all 11 locales**, and inspect Arabic RTL plus any locale that changes wrapping or behavior. Expand screenshots and interactions where a change or failure warrants it; a full Cartesian set of every locale × width × state is not the default. When the app exists, add repeatable Playwright checks for viewport correctness, the main controls, RTL, overflow, console errors, and screenshot capture. A test command that discovers zero tests is setup, not a passed QA gate.

While coding, use targeted searches, bounded file ranges, and diffs instead of rereading whole files or pasting unrelated source. Keep command output bounded and inspect the failing lines of logs; retain full artifacts on disk when needed. Reuse verified observations and rerun checks that a change could affect, without repeating an unchanged passing matrix. This saves working-context tokens during the full implementation cycle, not just at session start; it never waives a gate.

Keep tool use focused: use native Codex capabilities where they meet the gate, then project-specific skills/tools where they add required evidence. The Codex browser supports quick exploration; configured Playwright WebKit profiles supply repeatable iPhone screenshots and tests. Native `/review` is the code-review gate, not another installed skill; its findings do not replace screenshot, behavior, accessibility, or speed checks. A visual-verification pass checks actual screenshots independently of the code's apparent intent; an interaction pass checks real state transitions. These are responsibilities the main agent can perform sequentially. Tool installation, script availability, and successful checks are distinct states.

For long work, refresh [MEMORY.md](../MEMORY.md) at a material milestone before context is lost; at task end, remove stale status and reconcile affected topic docs. Do not rewrite the transcript. A repeatable failure goes to [LESSONS.md](../LESSONS.md), not to a growing list of ad hoc instructions in `AGENTS.md`. Promote a lesson into the always-loaded rules only when it is truly cross-task and important enough to justify that context cost.

If a check is technically unavailable, record the blocker and completed evidence. Do not silently skip it, replace it with source inspection, or assert an unverified guarantee. See [definition-of-done.md](definition-of-done.md) for the final gate.
