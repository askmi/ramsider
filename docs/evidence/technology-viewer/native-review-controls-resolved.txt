from pathlib import Path
from PIL import Image, ImageDraw


SOURCE = Path("design/references/technology_frame.PNG")
OUTPUT = Path("public/art/technology/frame-template.png")
SIZE = (954, 1649)
OPENING = (83, 186, 870, 1465)  # PIL inclusive rectangle; CSS x83:871, y186:1466.
DOT_BAND = (382, 110, 572, 140)
DOT_SPRITES = {
    "dot-active.png": (383, 111, 412, 140),
    "dot-inactive.png": (423, 111, 452, 140),
}


def main() -> None:
    source = Image.open(SOURCE)
    if source.size != SIZE or source.mode != "RGB":
        raise ValueError(f"Unexpected frame source: {source.size} {source.mode}")
    frame = source.convert("RGBA")
    ImageDraw.Draw(frame).rectangle(OPENING, fill=(0, 0, 0, 0))
    ImageDraw.Draw(frame).rectangle(DOT_BAND, fill=(0, 0, 0, 255))
    OUTPUT.parent.mkdir(parents=True, exist_ok=True)
    frame.save(OUTPUT, optimize=True)
    for filename, box in DOT_SPRITES.items():
        source.crop(box).save(OUTPUT.parent / filename, optimize=True)

    decoded = Image.open(OUTPUT).convert("RGBA")
    source_rgb = source.tobytes()
    output_rgb = decoded.convert("RGB").tobytes()
    alpha = decoded.getchannel("A")
    for y in range(SIZE[1]):
        for x in range(SIZE[0]):
            inside = 83 <= x <= 870 and 186 <= y <= 1465
            dots = 382 <= x <= 572 and 110 <= y <= 140
            if alpha.getpixel((x, y)) != (0 if inside else 255):
                raise AssertionError(f"Alpha mismatch at {(x, y)}")
            if not inside and not dots:
                offset = (y * SIZE[0] + x) * 3
                if output_rgb[offset : offset + 3] != source_rgb[offset : offset + 3]:
                    raise AssertionError(f"RGB mismatch at {(x, y)}")
    for filename, box in DOT_SPRITES.items():
        sprite = Image.open(OUTPUT.parent / filename)
        if sprite.tobytes() != source.crop(box).tobytes():
            raise AssertionError(f"Source-dot mismatch: {filename}")
    print(f"Exact frame outside opening and dot band: {OUTPUT} ({OUTPUT.stat().st_size} bytes)")

+## CHG-0060 — Сообщение заказчика о потере объёма изображений девайсов
+
+- **Дата / источник / статус:** 2026-10-06; CUSTOMER_FEEDBACK / DEFECT_REPORT; `OPEN`, диагностика без имплементации по запросу пользователя.
+- **Наблюдение → ожидание:** После перехода PNG→WebP заказчик воспринимает девайсы в фоне более плоскими; цвет текущей версии устраивает. Нужно выяснить причину и варианты локального восстановления объёма без нежелательного цветового сдвига и существенного ухудшения загрузки.
+- **Причина / ответственность / пропущенная проверка:** Причина визуального ощущения `UNKNOWN`: lossy-кодек, масштабирование, локальная резкость/контраст, исходный рендер и условия просмотра пока не отделены. Агент при CHG-0056/0058 проверил ICC, RGB/ΔE, браузерные кадры и скорость, но не ввёл отдельный критерий локальной фактуры/объёма именно на корпусах девайсов; это пропущенный контроль качества агента, а не вина заказчика. Подтверждения, что WebP вызвал эффект, пока нет.
+- **Промежуточная спецификация / следующий контроль:** Получить точные отмеченные заказчиком области; сравнить одинаково масштабированные color-managed PNG и текущий WebP в Pro/Max браузере, измерить локальный светлотный контраст/границы/фактуру и проверить варианты кодирования до художественной ретуши. Если проблема есть уже в master, отдельно рассмотреть мягкую маску предмета и коррекцию светлоты/микроконтраста, контролируя hue/chroma, края, ICC, размер и скорость. Никакие assets или код сайта в этой исследовательской задаче не изменять.
+- **Результат исследовательской сверки / файлы:** Без изменения изображений или кода; только эта запись. Существующие [color metrics](docs/evidence/art-webp/color-metrics.json) проверяют цвет, а не объём. Сохранённые Pro WebKit PNG/WebP кадры hero/compare осмотрены рядом; точные области жалобы заказчика не указаны, а общая ошибка цвета не позволяет судить о локальных бликах и фактуре. Документация Adobe подтверждает локальные маски/Clarity/Texture и Luminosity blending, документация Google — lossy/lossless WebP и параметры фильтра/quality. **Технический аппрув:** `PENDING` до локализованного A/B, доказанной причины и принятого решения. **Аппрув пользователя:** `NOT_RECORDED`.

# Development discipline: one request, complete result

The user's “one iteration” means one request to Codex should trigger a complete internal development cycle. It does **not** mean one code edit or one screenshot. Codex owns the repeated diagnosis and repair until all applicable gates pass. Do not transfer routine QA back to the user. A pass is evidence-based: there may be unknown bugs, but no known material mismatch, broken interaction, failing check, or unexamined requirement can be called done.

Work on a visual slice small enough to compare with the reference, then integrate **every slice in the requested scope** into the full scroll page. A passed slice is an internal milestone, not a handoff. At the start of each slice, make a compact coverage record from the render: content/art, controls and destinations, viewport/locale states, and relevant speed risks. Give each applicable check a result of pass, fail, or blocked with evidence; do not equate “not yet tested” with pass. For every stage, keep the target, observation, defect, fix, and recheck clear. A failed gate routes work back to the responsible stage and reopens downstream checks affected by the change.

Decide routine implementation details from the render, assets, code, and product brief without pausing for intermediate user approval. Reproduce visible reference copy in the local build for fidelity, with unverified factual claims tracked for publication. When a required media file, destination, credential, confirmed price/claim, or commerce behavior is genuinely absent, finish independent sections and checks, isolate the missing dependency, and ask only for the external input needed to finish that behavior or publish it. Do not invent it, silently omit a visible control, or mark that control complete. Keep a blocked gate distinct from a failed implementation that Codex can fix itself.

## Log changes as they happen

Follow the required schema and lifecycle in [CHANGELOG.md](../CHANGELOG.md). At scope inspection, search existing IDs; create a record for a new defect/change before implementation, with actual versus expected and source. At implementation, record the cause, mapping/specification → code chain and affected files; use `APPLIED_UNVERIFIED` until checks finish. Record each material failure and reopening immediately under the same ID. At verification, append actual commands/screenshots/results, date, verifier and the applicable auditor verdict. Only evidence-backed technical approval permits `VERIFIED`. Explicit user approval is recorded independently and is never inferred from silence. At delivery, reconcile the current status/index and link remaining open defects. Do this autonomously for small fixes as well as large tasks; use a compact record when appropriate.

Root-cause analysis must identify the agent decision/action, technical mechanism, missed control, evidence-backed responsibility and the behavior to change. Use the CHANGELOG classifications; missing or additional input is not automatically user fault. Unknown historical details stay unknown. Before similar work or rebuilding, load relevant causes/lessons and convert prevention into checks. Link repeatable errors to [Agent Eval](agent-evals.md); update case results only after actual runs, independently of fix approval.

Keep previous events intact when a conclusion changes. Backfilled records must identify their source and that checks are historical; missing evidence must remain explicit. Detailed reports can hold large evidence tables, but the journal must state the defect, solution and approval itself, not merely link to an unexplained report.
