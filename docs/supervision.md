# Independent stage-gate audit

For substantive project work, the main agent starts one non-editing `discipline_auditor` alongside scope inspection. The auditor makes an independent acceptance map from the requested scope and, for UI work, the approved render. The main agent then sends the same auditor a compact checkpoint at each applicable gate and waits for a finding **before advancing**. This is an event-driven review of work in progress, not a claim that a second agent sees or controls every tool call. The main agent remains responsible for implementation, browser evidence, fixes, `/review`, and final delivery. Trivial edits use only their relevant checks.

| Checkpoint | Auditor checks independently | Minimum evidence from the main agent |
| --- | --- | --- |
| Scope, before implementation | Requested coverage, acceptance method, unknown inputs; render sections, assets, and controls for UI work | Scope/affected-interface map, relevant reference crops for UI work, unresolved inputs |
| Each UI slice, before moving on | Real render against reference; Pro then Pro Max; visible controls and responsive risks | Reference crop and actual browser screenshots with viewport/DPR; changed files; visual comparison and retest result |
| Behavior and adaptation, if affected | Relevant interactions, keyboard/RTL/locales, safe areas and representative widths; for non-UI code, changed behavior and interfaces | Browser/test results, screenshots or traces for affected UI states; relevant tests and API results for other code |
| Review and optimization, if affected | Required static/tests/build checks and native `/review` for code changes; production speed and visual regression when affected | Diff, `/review` result or explicit unavailability for code, check output, and affected production measurements/recaptures |
| Final closeout | Full requested scope; assembled long-scroll QA for UI work; `MEMORY.md`/`LESSONS.md` updates where warranted; honest delivery claims; no failed or unexamined applicable gate | Consolidated pass/fail/blocked record, artifact paths, final screenshots where applicable, and draft evidence summary |

For each handoff, name the gate and changed scope, then give **paths to evidence**, concise command outcomes, and any worker-agent reports. The auditor reads the artifacts, not just the worker's claims. Its reply is `PASS`, `FAIL`, or `BLOCKED`, with the precise discrepancy, evidence location, responsible stage, and next check. An unrun feasible check or implementation defect is `FAIL`; `BLOCKED` is reserved for a concrete external dependency or tool failure preventing the evidence. On `FAIL`, the main agent fixes the issue, reruns the affected checks, and asks the auditor to recheck. On `BLOCKED`, it continues independent work and reports the exact dependency. An auditor's `PASS` cannot turn an absent screenshot, zero-test suite, or unmeasured performance target into proof. Include other subagents' outputs at the applicable checkpoint so their work is covered; the auditor does not automatically receive their transcripts.

The auditor profile requests a read-only sandbox and prohibits edits, but a parent session's live sandbox override can supersede that default; verify the effective setting when available and keep the no-edit assignment even if it cannot be enforced. Keep the agent focused on one checkpoint. Keep raw images and logs on disk, send paths and short excerpts, and avoid a second full implementation discussion. If a named custom agent cannot be selected, spawn a subagent with the same non-editing instructions. If subagents are unavailable, perform the same explicit evidence audit in the main thread and report the lost independent check; never imply a second agent ran. The first real site tasks should compare this workflow with the previous one using [agent evals](agent-evals.md): missed gates, material defects at delivery, user corrections, time, and token cost. Keep or adjust the audit cadence based on those results, without waiving the stage gates.

## Why this architecture

[Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) support project-scoped profiles and parallel read-heavy work, but each runs its own model/tools and adds cost. Their documented orchestration routes tasks and results through the parent; automatic continuous visibility into every parent and sibling action is not provided by this profile. [Codex hooks](https://learn.chatgpt.com/docs/hooks) can enforce narrow deterministic conditions, but `agent` hook handlers are currently skipped. A future `Stop` hook should be considered only after a runnable app and concrete, fast gate checks exist; it cannot judge visual fidelity from source code. For a true streaming observer that can steer active turns, a separate application would need to own the [App Server](https://learn.chatgpt.com/docs/app-server) event stream and use `turn/steer` or `turn/interrupt`. That additional controller is unjustified until evidence from agent evals shows the stage auditor is insufficient.
