## CHG0186 — Deep Research: iPhone Fullscreen and Small Screens, 2026-10-31

Запрос: повторно проверить причины проблем fullscreen на iPhone и обоснованность уже реализованного решения. Это исследование существующего кода, не новый редизайн и не публикация. Точные источники, статусы багов, SHA кода и дополнительные снимки: [iphone-window-research.json](evidence/video/iphone-window-research.json).

Вывод: для управляемой сайтом кнопки и заполнения доступного окна Safari выбран обоснованный вариант A — тот же playsinline video/HLS, собственный фиксированный слой, пропорциональный crop, сохранённый native fallback. Это не доказательство возможности скрыть все системные панели или работы на каждом iPhone/старой iOS/любом встроенном браузере.

1. **На iPhone различаются три режима.** Native video fullscreen открывает системный просмотрщик; Element Fullscreen переносит DOM-элемент с собственными controls; web full-window заполняет окно страницы. WebKit объявлял unprefixed ElementFullscreen в Safari16.4 именно для macOS/iPadOS. Запрос поддержки iPhone [206854](https://bugs.webkit.org/show_bug.cgi?id=206854) остаётся NEW на дату исследования; новый запрос328773 помечен duplicate, а не реализацией. Это ограничение платформы, не диагонали экрана. Наш iPhone window-путь не зависит от ElementFullscreen и не вызывает native entry. [WebKit16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/).

2. **playsinline — правильный способ оставить картинку в странице.** Он разрешает inline playback вместо автоматического native fullscreen. Он не является командой скрыть адресную строку и не запрещает все явные системные жесты. В нашем ProductFilm атрибут присутствует; меняется представление того же video, без смены source/audio/позиции. Публичный [Apple HTMLVideoElement API](https://developer.apple.com/documentation/webkitjs/htmlvideoelement) перечисляет entry/exit/state/presentation, но не web-сеттер fill/zoom системной картинки. Вывод об отсутствии такого управления относится к web API, не к возможностям нативных приложений. [WebKit inline policy](https://webkit.org/blog/6784/new-video-policies-for-ios/).

3. **Неравные пропорции требуют выбора между полями и обрезкой.** Для экрана844×390 кадр16:9 при contain занимает примерно693×390: остаётся около75px с каждой стороны. Cover сохраняет пропорцию и обрезает края. Отдельный файл19.5:9 подходит лишь под один аспект; браузерные панели и ориентация меняют доступный прямоугольник. Это геометрический вывод, а не ограничение конкретного бренда. [W3C object-fit](https://www.w3.org/TR/css-images-3/#the-object-fit).

4. **В Evolution поля частично записаны в видео.** Этот проектный факт установлен декодированными кадрами раньше исследования. CSS видит всю плоскость файла, включая чёрные пиксели. Поэтому простой cover не доказывает отсутствие полос. В нашем новом режиме отдельно учтена aperture y98..624/720: высота720/526 и сдвиг-50.138889%. Crop постоянный, включая финальный полный кадр; это согласованная потеря краёв, не утверждение «обрезаны только пустые пиксели». Native fallback сохраняет прежнее кадрирование. Ранее проверены реальные10/109s и all7. Источник/HLS не перекодировались.

5. **Маленькая полезная высота и safe area важнее модели телефона.** Safari меняет высоту при работе панелей. 100dvh/dvw предназначены для динамического viewport, а viewport-fit=cover и env(safe-area-inset-*) позволяют отделить картинку до краёв от безопасных кнопок. В коде это есть; popup привязан к измеренным высотам header/transport, строка controls растягивается в реально оставшуюся ширину. Ранее это обнаружило и исправило реальные overlap/overflow. При этом спецификация не требует непрерывного изменения dvh во время анимации chrome; клавиатура тоже может накладываться без изменения units. [WebKit15.4](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/), [safe areas](https://webkit.org/blog/7929/designing-websites-for-iphone-x/), [CSS viewport units](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths).

6. **Старый iOS и маленький экран — разные проверки.** Installed Next16.2.11 modern-browserslist-target.js содержит safari16.4; это совпадает с [официальным baseline](https://nextjs.org/docs/architecture/supported-browsers). Container queries/cqw появились в Safari16.0 ([WebKit](https://webkit.org/blog/13152/webkit-features-in-safari-16-0/)). Поэтому320×568 в современном WebKit не сертифицирует iOS15 на старом устройстве. Ни runtime Safari16.4, ни Safari15 отдельно здесь не запускались. Baseline framework — граница обещаний, не доказательство всех версий выше неё.

7. **Встроенный браузер может задавать собственные правила.** WKWebView host управляет [allowsInlineMediaPlayback](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/allowsinlinemediaplayback) и может задавать [customUserAgent](https://developer.apple.com/documentation/webkit/wkwebview/customuseragent). Страница не отменит запрет inline со стороны app. Наш выбор iPhone опирается на iPhone/iPod token: произвольный custom UA без него не даёт гарантии выбора window. Это условная граница, не воспроизведённый дефект обычного Safari и не утверждение о конкретном Telegram/desktop-mode клиента. Нативный путь вызывается непосредственно из gesture; для системных fullscreen API важна user activation ([WHATWG](https://fullscreen.spec.whatwg.org/)).

8. **Баги Safari реальны, но их нельзя приписывать клиенту без версии и воспроизведения.** [297779](https://bugs.webkit.org/show_bug.cgi?id=297779) описывает fixed/visual-viewport/system-component проблемы и имеет статус MOVED; поздние комментарии содержат разные результаты исправлений. [297182](https://bugs.webkit.org/show_bug.cgi?id=297182) про LiquidGlass gap имеет FIXED/landed commit, а не доказательство наличия ошибки в каждом современном релизе. [321330](https://bugs.webkit.org/show_bug.cgi?id=321330) NEW описывает повторные native fullscreen requests при pinch. Эти источники обосновывают проверку конкретного OS/browser и жестов, а не произвольные новые хаки в нашем коде. Автоматический orientation lock и скрытие chrome не обещаются.

Дополнительная проверка неизменённой production7: **24 PASS / 0 FAIL**, Evolution10s, RU+AR, двенадцать размеров на каждый язык:280×480,320×568/400,568×320/220,375×667/500/812,667×375/260,812×375/275. Реальный mobile WebKit/DPR3, современный iPhone UA; source/видео декодированы и QA беззвучна. Проверены actual CSS width/height, aperture coverage, 44px controls, отсутствие overflow, последний пункт popup с elementFromPoint и настоящим кликом, native adapter entry и сохранение source/time, повторный window entry. **Native API здесь подменён для наблюдения вызова; AVKit и физический SE/mini не эмулируются.** Снимки picture/menu сохраняются после завершения анимаций; начальный transitional capture исправлен в QA fixture, продукт не менялся.

Не предлагать ни ферму, ни покупку, ни PWA-install как обязательный незапрошенный шаг. Пока физическое подтверждение BLOCKED; новая опция локальна, не опубликована.
